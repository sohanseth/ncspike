# Spec — Phase 2.9: Image generation (with PRIVATE-tier on-device path)

**Status:** Draft v1.
**Owner:** main agent (chat pipeline, broker, tier policy, WebGPU
adapter, capability detection, fail-closed surface) + native dev for
the iOS / Android plugin source drops (same split as docs/11).
**Lovable-lane note:** this spec touches the chat pipeline, broker, and
PRIVATE-tier policy — all out of Lovable's lane. The native plugin
source lives under `ios/App/App/Plugins/NCImageGen*.swift` and
`android/app/src/main/java/.../plugins/NCImageGen*.kt`, generated by
`cap add` and not in either party's "do not touch" list. The chat-side
attachment surface (`chat_message_attachments`, `chat-attachments`
storage bucket) is already shipped (Lovable's vision merge,
20260508221834_*) and we reuse it verbatim — **no new attachment
storage table or bucket**.

> **Framing.** Image generation is the next obvious chat capability
> after vision-in. The honest constraint: today's on-device LLMs
> (Apple Foundation Models, Gemini Nano, Llama 3.2 via WebLLM) are
> all text-out only. So "PRIVATE generates an image" requires either a
> separate on-device image model (we ship one per platform) or
> fail-closed (we refuse). This spec ships **both** so the user always
> gets the strongest available path on their device, and a clear
> refusal everywhere else — never a silent cloud round-trip.

---

## 1. Why this phase exists

Three motivations, in priority order:

1. **Multimodal parity.** Lovable's Phase 2.6.5 vision merge gave the
   chat **image-IN** (drop a screenshot, ask about it). The natural
   complement is **image-OUT** ("make me a thumbnail of…", "redraw
   this in pixel-art style"). Without it the chat feels lopsided.
2. **Honest PRIVATE.** Today PRIVATE refuses any turn that involves an
   attachment because the chain runner has no on-device image-gen
   path. That refusal is correct (per docs/11 §9) but the user
   experience is "PRIVATE is broken for images." We can do better:
   on capable devices, PRIVATE actually generates the image locally;
   on incapable devices, the same refusal we ship today, but with a
   clearer message.
3. **Cost.** Image-gen is the most expensive single thing in the
   provider matrix (gpt-image-1 at $0.04/standard image, Gemini 2.5
   Flash Image at ~$0.039). On-device pushes that to $0 for users on
   capable hardware, which materially improves CPAUD (docs/05 §2 cap
   targets).

**Out of scope, explicit:**
- **Video generation.** Sora-class. Phase 4+.
- **Image editing with mask UI.** This phase ships text → image and
  image+text → image (img2img with text prompt). No brush mask, no
  inpainting UI surface. ControlNet/IP-Adapter is a Phase 3 follow-up.
- **Batch generation.** One image per turn. No "give me 4 variants"
  toggle in v1.
- **Resolutions > 1024². ** Capped at 1024×1024 server-side and
  768×768 on-device. Larger upscales are a separate feature.
- **Style transfer presets / LoRAs.** Plain prompt only in v1.

## 2. Architecture

The chat router (`src/server/inference/router.ts`) gains an
`imageOutCapable` flag per provider and a new **modality** field on
the chain config. The chain runner detects when a turn requires
image-out (see §3) and routes to the image-out chain instead of the
text chain. PRIVATE keeps its docs/11 client-side execution model:
when the client picks PRIVATE and the turn requires image-out, the
client runs the image model locally and only the resulting bytes
(plus zero-cost telemetry) ever leave the device.

```
User sends turn → resolve required modality
   ├── modality === "text-out"  → existing chat flow (unchanged)
   └── modality === "image-out"
         ├── badge === "private"?
         │     yes → streamOnDeviceImageGen() (client-side)
         │              ├── detectImageGenCapability()  → pick adapter
         │              ├── prepareOnDeviceImageTurn()   → server-fn:
         │              │     cap-check, persist user msg + attachments,
         │              │     broker @ tier -1 (image-only categories),
         │              │     return {prompt, init_image?, ids}
         │              ├── runApplePlayground() | runMediaPipeImageGen()
         │              │     | runJanusProWebGPU() | runSDTurboWebGPU()
         │              │     → produce image bytes locally
         │              ├── uploadAttachment(bytes)      → server-fn:
         │              │     write to chat-attachments bucket under
         │              │     {user_id}/gen/{message_id}.png
         │              └── finalizeOnDeviceImageTurn()  → server-fn:
         │                    persist assistant msg with attachment ref +
         │                    zero-cost telemetry + audit log
         │     no  → fail-closed UI (capability missing)
         │
         └── badge in {flash, pro, genius}
               → existing chain runner with image-out adapters
                 (Gemini 2.5 Flash Image, gpt-image-1)
               → adapter persists attachment via chat-attachments bucket
```

The text chain and image chain are **disjoint chains, not a single
chain that switches modality mid-fallback.** A failed image-out
generation does NOT silently fall back to a text apology — it
surfaces an explicit error so cost and behavior stay legible.

## 3. Modality detection

Two triggers, in order:

1. **Explicit toggle.** A small "image" pill in the ChatPanel
   composer next to the badge picker. When set, the next turn forces
   `modality = "image-out"`. Resets to text after send. This is the
   reliable path and the one the docs surface.
2. **Heuristic auto-trigger.** When the toggle is off but the prompt
   matches a small allow-list of intent verbs in combination with an
   image noun: `(generate|create|make|draw|sketch|render|design)
   .*(image|picture|thumbnail|icon|logo|illustration|diagram)`, the
   client pre-fills the toggle with a one-tap confirm chip
   ("Generate as image?"). If the user dismisses or sends without
   confirming, the turn runs as text-out.

The heuristic is intentionally conservative — false negatives
(missing an obvious image request) are recoverable (toggle and
resend), false positives (cloud image gen on a casual phrase) cost
real money.

The list lives in `src/lib/image-intent.ts` and is unit-tested
against a fixture corpus of 50 prompts (25 image-intent, 25 not).

## 4. Tier -1 image policy

PRIVATE = tier -1 (docs/11 §3) is preserved. The broker, when called
for an image-out turn at tier -1, must:

- Select **only image-relevant trait categories** (style preferences,
  prior generated-image themes, accessibility traits like color
  blindness). Identity / household / health categories are **never**
  injected into an image prompt regardless of tier — image generators
  are notoriously prompt-leaky and often render text from the prompt
  into the image itself.
- Refuse to assemble if the trait sheet contains any face-photo
  embedding referencing the user (defense against "render a picture
  of me").
- The output image is **never** sent through any face-detection or
  recognition step server-side. Only mime + storage_path + dimensions
  are persisted.

Allow-list of image-broker categories (additive to docs/06 §B4 if/when
that table grows):

| Category | Tier -1 (PRIVATE) | Tier 0/1 (cloud) |
| --- | --- | --- |
| `style_preferences` | ✅ | ✅ |
| `prior_image_themes` | ✅ | ✅ |
| `accessibility_visual` | ✅ | ✅ |
| `identity` | ❌ | ❌ |
| `household` | ❌ | ❌ |
| `health` | ❌ | ❌ |
| `wellness` | ❌ | ❌ |

(All other categories: ❌ for image-out, regardless of tier.)

## 5. On-device image-gen pathways

Same three-platform shape as docs/11 §1, but each pathway is a
distinct image-gen model:

| Pathway | Platform | Model | Adapter ID | Approx size | Time on capable device |
| --- | --- | --- | --- | --- | --- |
| Apple Image Playground | iOS 18.2+, Apple Intelligence on, A17 Pro / M-series | Apple's on-device "Sketch / Animation / Illustration" generators | `imagegenAppleIP` | 0 (OS-bundled) | 2–5 s for 1024² |
| MediaPipe Image Generator | Android 13+, Snapdragon 8 Gen 2+ / Tensor G3+ | Google's distilled SD (~1 GB INT8) | `imagegenAndroidMP` | ~1.0 GB | 4–8 s for 512², ~15 s for 768² |
| Janus-Pro 1B (WebGPU) | Any browser with WebGPU + ≥6 GB shared GPU memory | DeepSeek Janus-Pro 1B (Apache 2.0), unified vision-in + image-out | `imagegenWebGPUJanus` | ~2.0 GB (q4f16) | 10–20 s for 768² on M1 |
| SD-Turbo (WebGPU, fallback) | Any browser with WebGPU + ≥4 GB shared GPU memory, where Janus-Pro 1B fails to load | Stability AI SD-Turbo distilled (1-step), CC-licensed for personal/non-commercial | `imagegenWebGPUSDT` | ~1.5 GB (q4) | 3–6 s for 512² on M1 |

**Selection priority** (run in order, take first that returns
`available: true`):

1. `imagegenAppleIP` (best UX, zero memory, Apple-style output)
2. `imagegenAndroidMP` (best UX on Android)
3. `imagegenWebGPUJanus` (best capability — also supports img2img
   with a reference image, which the native paths don't do well)
4. `imagegenWebGPUSDT` (smallest fallback, text→image only)

If none returns `available: true`, **fail closed.** Show the same
honest UI from docs/11 §9 with image-specific copy:

> "Image generation isn't available on this device for the PRIVATE
> badge. To keep your prompt on-device, only certain hardware can
> run an on-device image model. Switch to FLASH, PRO, or Genius to
> generate images via a hosted provider, or use this device's text
> chat with PRIVATE."

The same UI never silently switches the badge for the user.

## 6. Capability detection contract

Mirrors `detectOnDeviceCapability` from docs/11 §4, in a separate
module `src/lib/on-device-imagegen.ts` so the text and image
detection paths can evolve independently.

```ts
export type ImageGenAdapterId =
  | "imagegenAppleIP"
  | "imagegenAndroidMP"
  | "imagegenWebGPUJanus"
  | "imagegenWebGPUSDT";

export interface ImageGenCapability {
  adapter: ImageGenAdapterId;
  available: boolean;
  // Why unavailable, surfaced in the fail-closed toast (string only,
  // no structured codes — keeps the message authoritative).
  reason?: string;
  // Best supported output size for this adapter on this device.
  maxDim: 512 | 768 | 1024;
  // True if the adapter accepts an init image (img2img). Drives the
  // "edit this attachment" affordance in the composer.
  supportsImg2Img: boolean;
  // First-run download cost in MB. 0 for OS-bundled adapters. Surfaces
  // as a one-time consent before model load.
  firstRunDownloadMB: number;
}

export async function detectImageGenCapability(): Promise<ImageGenCapability>;
```

Detection rules per adapter:

- **`imagegenAppleIP`:** `Capacitor.isNativePlatform()` && iOS && plugin
  reports `imagePlaygroundAvailable: true` (the plugin calls
  `ImagePlaygroundViewController.isAvailable` on iOS 18.2+).
- **`imagegenAndroidMP`:** native + Android + plugin reports
  `mediaPipeImageGenAvailable: true` (checks for the MediaPipe
  Image Generator task model file presence after first install).
- **`imagegenWebGPUJanus`:** `navigator.gpu` exists + `requestAdapter`
  returns an adapter + `adapter.limits.maxBufferSize ≥ 2 GB` +
  `navigator.deviceMemory ≥ 6` (gated on Chrome/Edge desktop +
  Safari 18+; a runtime probe loads the smallest tensor and times
  out at 5 s — if that fails, fall to SD-Turbo).
- **`imagegenWebGPUSDT`:** same WebGPU probe but with
  `adapter.limits.maxBufferSize ≥ 1 GB`.

Detection result is cached per session in `sessionStorage` keyed by
`nc:imagegen:cap:v1`. A "Re-detect" button lives in
`/workspace/settings/privacy` next to the existing on-device tier
diagnostics.

## 7. Native plugin contracts

### 7.1 iOS — `NCImageGenApplePlaygroundPlugin.swift`

Capacitor plugin that wraps `ImagePlaygroundViewController` (iOS
18.2+). Lives in `ios/App/App/Plugins/`. Build-ready source ships
in this spec; main agent does not commit it because the iOS project
is generated by `cap add ios` per docs/04.

```swift
import Capacitor
import ImagePlayground
import UIKit

@objc(NCImageGenApplePlaygroundPlugin)
public class NCImageGenApplePlaygroundPlugin: CAPPlugin {

    @objc func isAvailable(_ call: CAPPluginCall) {
        if #available(iOS 18.2, *) {
            call.resolve(["available": ImagePlaygroundViewController.isAvailable])
        } else {
            call.resolve(["available": false, "reason": "Requires iOS 18.2+"])
        }
    }

    @objc func generate(_ call: CAPPluginCall) {
        guard #available(iOS 18.2, *), ImagePlaygroundViewController.isAvailable else {
            call.reject("ImagePlaygroundUnavailable")
            return
        }
        guard let prompt = call.getString("prompt") else {
            call.reject("Missing 'prompt'")
            return
        }
        let style = call.getString("style") ?? "illustration"  // "sketch" | "animation" | "illustration"

        DispatchQueue.main.async {
            let vc = ImagePlaygroundViewController()
            vc.concept = prompt
            vc.style = self.styleFor(style)
            vc.delegate = ImageGenDelegate { result in
                switch result {
                case .success(let image):
                    guard let data = image.pngData() else {
                        call.reject("PNGEncodeFailed"); return
                    }
                    call.resolve(["pngBase64": data.base64EncodedString()])
                case .failure(let err):
                    call.reject(err.localizedDescription)
                }
            }
            self.bridge?.viewController?.present(vc, animated: true)
        }
    }

    private func styleFor(_ raw: String) -> ImagePlaygroundStyle { /* … */ }
}
```

**Important security note for the iOS plugin:** the user is the only
party that can confirm the generated image (Image Playground's UI
requires a tap to accept). This is intentional — Apple's design
guarantees no silent generation. Our adapter inherits that property
and surfaces "image generation cancelled" if the user dismisses.

### 7.2 Android — `NCImageGenMediaPipePlugin.kt`

Wraps Google's MediaPipe Image Generator task. Model file
(`stable_diffusion.tflite`, ~1 GB, INT8) is downloaded on first use
into the app's private files dir.

```kotlin
package com.neuralconnexions.app.plugins

import com.getcapacitor.JSObject
import com.getcapacitor.Plugin
import com.getcapacitor.PluginCall
import com.getcapacitor.PluginMethod
import com.getcapacitor.annotation.CapacitorPlugin
import com.google.mediapipe.tasks.vision.imagegenerator.ImageGenerator
import com.google.mediapipe.tasks.vision.imagegenerator.ImageGeneratorOptions
import java.io.File
import java.util.Base64

@CapacitorPlugin(name = "NCImageGenMediaPipe")
class NCImageGenMediaPipePlugin : Plugin() {

    private var generator: ImageGenerator? = null

    @PluginMethod
    fun isAvailable(call: PluginCall) {
        val modelFile = File(context.filesDir, "stable_diffusion.tflite")
        val ret = JSObject()
        ret.put("available", modelFile.exists())
        ret.put("modelPresent", modelFile.exists())
        call.resolve(ret)
    }

    @PluginMethod
    fun ensureModel(call: PluginCall) {
        // Download stable_diffusion.tflite from a known URL (provided by
        // Google's MediaPipe model zoo) into context.filesDir.
        // Show progress via notifyListeners("downloadProgress", ...).
        // Idempotent: skip if file exists and SHA-256 matches.
        // Implementation: standard OkHttp download with verification.
        call.resolve()
    }

    @PluginMethod
    fun generate(call: PluginCall) {
        val prompt = call.getString("prompt") ?: return call.reject("Missing 'prompt'")
        val seed = call.getInt("seed") ?: 0
        val steps = call.getInt("steps") ?: 8
        val modelFile = File(context.filesDir, "stable_diffusion.tflite")
        if (!modelFile.exists()) return call.reject("ModelNotInstalled")

        if (generator == null) {
            val opts = ImageGeneratorOptions.builder()
                .setImageGeneratorModelDirectory(modelFile.parent!!)
                .build()
            generator = ImageGenerator.createFromOptions(context, opts)
        }
        try {
            val out = generator!!.generate(prompt, steps, seed)
            val png = out.generatedImage().convertToByteArray()  // png encode helper
            val ret = JSObject()
            ret.put("pngBase64", Base64.getEncoder().encodeToString(png))
            call.resolve(ret)
        } catch (t: Throwable) {
            call.reject(t.message ?: "GenerateFailed")
        }
    }
}
```

The plugin's `ensureModel` is invoked once on first PRIVATE
image-gen attempt, behind a one-time consent dialog (~1 GB
download).

### 7.3 WebGPU — `src/lib/imagegen-webgpu-janus.ts` and `imagegen-webgpu-sdt.ts`

Pure TS, runs in the browser. Both adapters share the same lifecycle:

```ts
export interface WebGPUImageGenAdapter {
  load(opts: { onProgress: (pct: number) => void; signal: AbortSignal }): Promise<void>;
  generate(opts: {
    prompt: string;
    initImage?: Blob;        // SDT ignores this; Janus uses it
    width: number;
    height: number;
    steps?: number;
    signal: AbortSignal;
  }): Promise<Blob>;          // PNG bytes
  unload(): Promise<void>;    // free GPU memory
}
```

Janus uses `@huggingface/transformers` (transformers.js v3+) with
its WebGPU backend. SD-Turbo uses `mlc-ai/web-stable-diffusion`
(MLC's WebGPU SD runtime, mature and documented). Both pin a known
model revision (no auto-update — model behavior changes are spec
changes).

Models are cached in OPFS (Origin Private File System) under
`/nc/imagegen/{adapter}/{revision}/`. First-run download surfaces
via the same `load_progress` ChatStreamEvent we already shipped
for WebLLM (just-fixed bug — see commit history).

## 8. Cloud adapter surface (FLASH / PRO / Genius)

Two new provider modules under `src/server/inference/`:

- `gemini-image.ts` — Gemini 2.5 Flash Image (`gemini-2.5-flash-image-preview`).
  REST endpoint, accepts text + optional reference images, returns
  PNG bytes. ~$0.039 per 1024² image (priced per spec'd token rate).
- `openai-image.ts` — gpt-image-1. Accepts prompt + optional mask /
  reference. Returns PNG bytes. $0.04 standard / $0.17 high-fidelity.

**Chain mapping** (added to `router.ts`):

| Badge | Image-out chain | Notes |
| --- | --- | --- |
| FLASH | `geminiImage` only | Cheapest cloud option, fast (3–5 s). |
| PRO | `geminiImage` → `openaiImageStandard` | Fall back if Gemini errors. |
| Genius | `openaiImageHigh` → `geminiImage` | Highest quality first. (Genius is locked for free tier per docs/11 — same gating applies.) |
| PRIVATE | on-device only (§5) | Never falls back to cloud. |

The cloud adapters reuse `chat_message_attachments` for the output:
the server fn writes the PNG to the `chat-attachments` bucket at
`{user_id}/gen/{message_id}.png` and inserts an attachment row with
mime + dimensions. The chat bubble renders it via the existing
attachment-render path Lovable shipped.

## 9. Cost model

Targets and ceilings (per docs/05 §2 CPAUD framework):

| Path | Cost per image | Notes |
| --- | --- | --- |
| PRIVATE (any on-device adapter) | $0 | First-run download cost is amortised — not billed. |
| FLASH | ~$0.039 | Gemini 2.5 Flash Image, 1024². |
| PRO | ~$0.039 → $0.04 fallback | Gemini first, OpenAI standard fallback. |
| Genius | $0.17 | OpenAI gpt-image-1 high-fidelity. |

**Per-user cap.** New entry in `FREE_TIER_CAPS`:

```ts
imagesPerDay: { flash: 5, pro: 3, genius: 0 }
```

Genius image-out is locked for free tier exactly like Genius text
(consistent with docs/11 §3.2). Cap is enforced in `assertCap`
before any provider call. Cap-exceeded surfaces the same toast
pattern as text caps.

**CPAUD model.** Worst-case daily cost per active user, all on
cloud, no PRIVATE: `5 × $0.039 + 3 × $0.04 = $0.32`. Combined
with text CPAUD ceiling ($1.50 — docs/05 §2), image-out adds
**$0.32 / user / day** worst case, ~$0.10 expected (most users
won't hit caps).

If PRIVATE adoption hits even 30% on capable devices, expected
image CPAUD drops to ~$0.07 / user / day. PRIVATE adoption is the
main lever.

A new pricing row goes in `src/server/inference/pricing.ts` with a
synthetic per-image cost (bypasses the per-token formula since
image gen prices per output, not per token).

## 10. Persistence + telemetry

Reuses Lovable's existing `chat_message_attachments` table. No new
migration required for the attachment surface. One small migration
adds an `image_modality` enum column to `inference_usage` so the
CPAUD viewer can split text vs image cost without parsing
provider-specific column patterns:

```sql
-- supabase/migrations/20260518000000_phase29_inference_modality.sql
do $$ begin
  if not exists (select 1 from pg_type where typname = 'inference_modality') then
    create type public.inference_modality as enum ('text', 'image');
  end if;
end $$;

alter table public.inference_usage
  add column if not exists modality public.inference_modality
    not null default 'text';

create index if not exists inference_usage_modality_idx
  on public.inference_usage (user_id, day_bucket, modality);
```

Idempotent: `if not exists` guards everywhere. `delete_user_data()`
needs no change — the column is on a table already covered by the
RPC. The GDPR per-user-table-coverage test stays green because no
new tables are added.

For PRIVATE on-device generations the server fn `finalizeOnDeviceImageTurn`
inserts an `inference_usage` row with `provider_used = '<adapter_id>'`,
`modality = 'image'`, and `cost_usd = 0` — exactly mirroring how
docs/11 §8 records text PRIVATE turns.

## 11. Fail-closed surface

The most important UI guarantee: a user who picks PRIVATE and asks
for an image either gets a real on-device image, or sees a clear
refusal — never a quiet cloud round-trip and never a silent badge
swap.

States the composer/bubble can show, in order of preference:

1. **Eligible + model loaded** → normal stream with a load-progress
   bar (reusing the just-fixed `load_progress` ChatStreamEvent
   path) only on first run.
2. **Eligible + model needs first-run download** → consent dialog
   with explicit size ("MediaPipe image model, ~1 GB, one-time
   download to your phone, never sent to any server"). User
   accepts → download → generate. User declines → state #4.
3. **Eligible + model load failed** → toast: "Couldn't load the
   on-device image model on this device. Switch to FLASH, PRO, or
   Genius to generate images via a hosted provider." Composer's
   image toggle stays on so the next badge tap re-triggers.
4. **Ineligible (no capable adapter)** → composer's image toggle
   shows a small lock icon when PRIVATE is selected. Tapping
   reveals the docs/11-style explanation. Switching badge clears
   the lock.
5. **Generation in progress, user cancels** → abort the WebGPU /
   native call via AbortSignal, do NOT persist a partial
   attachment, surface "cancelled" in the bubble. PRIVATE never
   leaves a half-generated PNG in storage.

There is **no silent fallback from PRIVATE to FLASH** for image
output, ever. This is the same contract as docs/11 §9 for text.

## 12. Test plan

- **Unit:** `tests/unit/image-intent.test.ts` (50-prompt heuristic
  fixture); `tests/unit/imagegen-cap.test.ts` (capability detection
  matrix mocked).
- **Leak suite extension:** `tests/leak-suite/image-broker.test.ts`
  — assert the image-broker NEVER injects identity/household/health
  categories into an image prompt at any tier. 200 synthetic prompts
  × 4 tiers, zero leaks.
- **Schema banned-keys (new):** an extension of the existing
  schema-banned-keys test verifying no `face_*` or `photo_*` keys
  exist in any image-broker output schema.
- **GDPR coverage:** no new tables, so existing
  per-user-table-coverage stays green automatically. The real-DB
  roundtrip test gets a SEED for PRIVATE-generated attachment rows
  (already covered by the chat_message_attachments seed added in
  the just-shipped fix — no further test work needed).
- **E2E (Playwright, capable browser):** generate an image via
  PRIVATE on a WebGPU-enabled headless Chrome with a stub adapter
  that returns a fixed PNG. Assert: zero outbound network calls
  during generation; attachment row written; attachment bytes match
  the stub's PNG.
- **Cost regression:** synthetic chain run with image modality on
  each badge, asserting `inference_usage.cost_usd` matches the
  pricing table within 0.1¢.

Acceptance: all of the above pass + manual smoke on one Apple
Intelligence-capable device, one Snapdragon 8 Gen 2+ Android, and
desktop Chrome with WebGPU enabled.

## 13. Phasing & sequence

Five steps, each ~1–2 days. Steps 1–3 are required for the feature
to ship; 4–5 are progressive enhancements that can land in
follow-up turns.

1. **Cloud image-out for FLASH / PRO / Genius** — the smallest
   thing that moves the user's reported need ("multimodal chat").
   Adapters, chain mapping, cap, modality enum migration, pricing
   row, attachment-render reuse. PRIVATE shows the
   "ineligible" lock with a clear message.
2. **WebGPU SD-Turbo for desktop PRIVATE.** Smallest on-device
   adapter. Validates the WebGPU detection, OPFS caching, and the
   load-progress UI for image. Quality is "good enough to
   demonstrate."
3. **Apple Image Playground native plugin.** Best mobile UX. Ships
   alongside iOS native build per docs/04 runbook.
4. **MediaPipe Image Generator native plugin** (Android).
5. **Janus-Pro 1B WebGPU adapter** (replaces SD-Turbo as primary
   WebGPU when the device meets the higher memory bar; adds
   img2img support).

Image-IN on PRIVATE — replacing Lovable's cloud vision call with
Phi-4-multimodal or Gemma 3 4B vision via WebLLM — is a separate
spec (docs/13?) that this phase deliberately does not touch.

## 14. Open questions

1. **Apple Image Playground style limits.** Output is locked to
   Apple's three styles. Do we surface that limitation in the
   composer when the active adapter is `imagegenAppleIP`, or just
   accept the user's prompt and let Apple's UI do the styling?
   *(Recommendation: surface — explicit > magic.)*
2. **MediaPipe model download UX.** ~1 GB is large; some users on
   metered connections will reasonably refuse. Do we surface a
   "WiFi only" toggle and pause/resume? *(Recommendation: yes for
   v1; reuses Capacitor's network state API.)*
3. **OPFS quota on iOS Safari.** OPFS is 60% of free disk by
   default; on a phone with 5 GB free that's 3 GB — fine for
   SD-Turbo (~1.5 GB) but tight for Janus-Pro 1B (~2 GB). Do we
   prefer Apple Image Playground over WebGPU on iOS even when both
   are available? *(Recommendation: yes — Apple IP is the better
   path on iOS in every dimension.)*
4. **NSFW / safety classifier.** All cloud providers (Gemini,
   OpenAI) have built-in safety. On-device adapters do not. Do we
   ship a tiny on-device NSFW classifier (NSFWJS / Apple's
   on-device VNClassifyImage) and refuse to persist images that
   trigger it on PRIVATE? *(Recommendation: yes for v1 —
   defense-in-depth, runs on-device so no privacy regression.)*
5. **Provider fallback semantics for cloud chain.** When Gemini
   image errors mid-stream, do we silently retry on OpenAI
   (current text-chain behavior) or surface the failure? Image
   gen is more user-visible than a missed text token; arguably the
   user should know which provider drew their thumbnail.
   *(Recommendation: silent fallback within a tier, but the
   message footer always names the actual provider used.)*

These are the five decisions that genuinely need a human call
before implementation begins. Everything else in this spec is
build-ready.

## 15. v1 lock (decisions made 2026-05-09)

User answered the §14 questions and asked for one feature beyond
the original scope: **img2img edit** ("here's my photo, try a new
hairstyle"). The locked direction is below. Anything not in this
section stays as drafted in §1–§14.

### 15.1 Locked answers to §14 questions

1. **Apple IP style limit** — moot. v1 does not use Apple Image
   Playground for the `try a new hairstyle` flow because Apple IP
   is text-to-image only. We still expose Apple IP for pure
   text-to-image turns on iOS (it stays the priority-1 adapter
   for that subset).
2. **MediaPipe download UX** — no toggle, download whenever the
   user first hits an on-device image turn. (User confirmed after
   I clarified the model downloads once, not per request.)
3. **iOS preference** — Apple IP for text-to-image; the img2img
   path on iOS is a separate adapter (see §15.3).
4. **NSFW classifier** — yes, on-device, refuse to persist
   flagged outputs. NSFWJS in the WebGPU path; Apple's
   `VNClassifyImageRequest` on iOS; MediaPipe Image Classifier
   with NSFW labels on Android. This runs after generation,
   before write to storage. PRIVATE never sends an unfiltered
   image off-device, even to its own bucket, on a flagged result.
5. **Cloud fallback** — **never.** PRIVATE turns are on-device
   end-to-end or they fail closed with an honest message. No
   silent retry against FLASH / PRO / Genius for PRIVATE turns,
   even for image. (This overrides the §14.5 recommendation.)

### 15.2 Honest capability matrix for img2img on-device, mid-2026

User cited FLUX.1 Kontext, HunyuanImage-3.0, Core ML, MediaPipe,
and ControlNet. The field is genuinely moving, but a sober look
at sizes vs. phone constraints:

| Model | Min size (quantized) | Realistically runs on | Img2img edit quality |
| --- | --- | --- | --- |
| FLUX.1 Kontext [dev] | ~6 GB Q4, ~12 GB FP8 | Desktop GPU only | Best in class, but desktop |
| HunyuanImage-3.0 (80B MoE) | >40 GB | Server / multi-GPU only | Not a phone option |
| SDXL + InstructPix2Pix | ~4 GB Q4 | Desktop WebGPU; M-series Mac | Good |
| SD 1.5 + ControlNet (depth/pose/lineart) | ~1.5 GB Q4 | Phone-feasible (Core ML / MediaPipe / WebGPU) | Workable but not photorealistic for face/hair edits |
| Apple Image Wand | OS-bundled, no public API | iPhone 15 Pro+ | Inpainting only, no public app entry today |

The "try a new hairstyle on my actual face" use case is the
hardest cell in this table — face/hair edits are exactly where
small models fall down. v1 ships the best on-device model that
fits each platform's memory + compute envelope and is honest
about quality.

### 15.3 What v1 ships, per platform

**iOS (native, Capacitor):**
- Text-to-image: Apple Image Playground (`imagegenAppleIP`).
- Img2img edit: **Core ML SD 1.5 + ControlNet** (depth + lineart
  conditioning) packaged as a Capacitor plugin
  `NCImageEditCoreMLPlugin.swift`. ~1.5 GB on-device download
  on first use. 10–20 s per edit on iPhone 15 Pro / A17 Pro+.
  Older iPhones: capability detection returns `available:false`
  with reason `"This iPhone doesn't have enough Neural Engine
  headroom for on-device image editing. Upgrade to iPhone 15 Pro
  or newer."` — fail-closed, no cloud fallback.

**Android (native, Capacitor):**
- Text-to-image: MediaPipe Image Generator (`imagegenAndroidMP`).
- Img2img edit: **MediaPipe Image Generator + ControlNet plugin
  task** (Google added the conditioning plugin in late 2025).
  Same ~1 GB base + ~200 MB ControlNet weights. Snapdragon
  8 Gen 2+ / Tensor G3+ only. Below that: fail-closed.

**Web (WebGPU desktop):**
- Text-to-image: Janus-Pro 1B if `maxBufferSize ≥ 2 GB`, else
  SD-Turbo.
- Img2img edit: **WebGPU SDXL + InstructPix2Pix** (~4 GB) for
  desktop-class GPUs; **WebGPU SD 1.5 + ControlNet** (~1.5 GB)
  for mid-tier. Capability probe picks one.

**Web (mobile browser, no WebGPU):**
- No on-device path. Fail-closed with the standard message.

### 15.4 NSFW pipeline (locked)

Run the on-device classifier on the **output** image (not the
input — users may legitimately edit photos containing nudity in
art / medical / parenting contexts they own). On a flagged
output:

1. Discard the tensor in memory before write.
2. Persist a `chat_messages` row with `content` set to a
   placeholder ("Image was generated but blocked by the on-device
   safety classifier. The image was not saved.") and
   `image_blocked: true` in a new `inference_usage.metadata`
   field.
3. Surface a toast: "Generated image was blocked by on-device
   safety filter. Try a different prompt."
4. No telemetry leaves the device about *what* was flagged —
   only the count.

### 15.5 What is NOT in v1 (deferred)

- FLUX.1 Kontext [dev] integration — desktop-only, revisit when
  a phone-class quantization (≤2 GB) ships.
- HunyuanImage-3.0 — server-only at any quantization in 2026.
- Apple Image Wand integration — no public API; revisit when
  Apple opens it.
- Multi-image edits (style transfer from photo A onto photo B) —
  v1 is single-input edit only.
- Animation / short video — out of scope for Phase 2.9.

### 15.6 Storage budget — locked

User chose **same no-toggle policy for both models**: download
the text-to-image model when the user first hits a text-to-image
turn, download the img2img edit model when the user first hits
an attached-image edit turn. No opt-in dialog either time.
Total on-device cache after both: ~2.5 GB on iOS / Android,
up to ~5.5 GB on web (SDXL + IP2P). Implementation must:

- Show a clear progress UI on first download of each model
  (reuses the load-progress event wiring already shipped in
  Phase 2.8).
- Surface total cache size + a "Clear on-device image models"
  button in `/workspace/settings/privacy` so a user who regrets
  the storage cost has a one-tap reclaim path.
- Fail closed if the device has less free disk than the model
  being downloaded — never partial-write.

Spec is now fully locked. Ready for implementation as a
multi-day phase (native plugins on iOS + Android, WebGPU
pipelines on web, NSFW classifier integration, capability
detection, persistence, telemetry). That is its own task; this
session does not start it.

stays green at every step.

  - `detectImageIntent` lives in `src/lib/image-intent.ts` and is
    re-exported from `src/server/inference/imagegen.ts` so client
    and server agree on classification.
  - `chat_message_attachments.attachment_kind` (`'image_in' |
    'image_out'`) — see migration `20260518000000_phase29a_attachment_kind.sql`.
  - `detectImageGenCapability()` returns `{ available, adapter }`
    or `{ available:false, reason }` per device.
  - Tests: `phase29a-image-gen-capability`, `phase29a-modality-fork`,
    `phase29a-attachment-kind-migration`.

- **Slice b — PRIVATE on-device WebGPU image-gen end-to-end (shipped, Phase 2.9b)**
  - `@huggingface/transformers` installed; WebGPU SD-Turbo
    adapter in `src/lib/imagegen-adapters/webgpu-sd-turbo.ts`.
  - `pickAdapter('webgpu-sd-turbo')` resolves to the SD-Turbo
    adapter; every other adapter id returns null (fail-closed,
    no silent fallback to a hosted provider).
  - Client dispatcher `src/lib/on-device-private-image.ts`:
    capability probe → `prepareOnDeviceTurn` (cap + persist) →
    WebGPU adapter → `classifyGeneratedImage` gate → user-token
    Supabase upload to `${userId}/imagegen/${uuid}.${ext}` →
    `finalizeOnDeviceImageGenTurn` (assistant row + attachment
    row tagged `attachment_kind='image_out'` + zero-cost
    telemetry row in `inference_usage`).
  - The finalize server-fn takes the **storage path**, never the
    bytes — preserving the on-device promise (no image bytes ever
    transit our server).
  - Routing: `chat-stream.ts` forks PRIVATE + image-intent +
    no-attachments to the on-device dispatcher BEFORE the

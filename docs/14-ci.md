# CI matrix

This doc lists every GitHub Actions workflow this repo runs and what each
one is responsible for. The non-obvious ones (anything that touches a real
external system, anything destructive, anything gated) are spelled out in
detail.

## "Real DB" means two surfaces

The real-DB regression suites — `tests/leak-suite/gdpr-roundtrip-realdb.test.ts`
(per-table coverage of `delete_user_data()`) and
`tests/leak-suite/cap-race-realdb.test.ts` (the
`reserve_inference_slot` / `finalize_inference_usage` /
`release_inference_slot` SQL trio) — are run by CI against **two**
distinct database surfaces. Both surfaces gate on the same
`GDPR_REAL_DB_URL` env var; the only difference is which Postgres that
URL points at.

| Surface              | Workflow              | Trigger                                                           | What it catches                                                                                                                       |
| -------------------- | --------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Ephemeral local PG   | `gdpr-real-db.yml`    | every PR + push that touches the relevant paths                   | SQL syntax, broken function bodies, drifted RPC return signature, idempotency regressions on a fresh DB                               |
| Staging Supabase clone | `gdpr-supabase.yml` | push to `main`, `workflow_dispatch`, opt-in PR label              | Supabase-specific drift: `auth.users` triggers, RLS vs `service_role`, real FK cascades, extension availability, advisory-lock collisions |

Cost control: the staging-clone job is destructive (it wipes
`auth.users` and every per-user table in `beforeEach`) and burns a real
Supabase project's quota, so it never runs on every PR.

## `gdpr-real-db.yml` — local-Postgres GDPR round-trip

Spins up an ephemeral PostgreSQL 16 cluster in the runner's tmp dir,
applies `tests/leak-suite/fixtures/auth-shim.sql` to fake the bits of the
Supabase `auth` schema we depend on, applies every
`supabase/migrations/*.sql` under `ON_ERROR_STOP=1`, then runs
`tests/leak-suite/gdpr-roundtrip-realdb.test.ts`.

**Catches:** SQL syntax errors, broken `delete_user_data()` body, drifted
RPC return signature, missing per-table DELETE, idempotency regressions
(re-running migrations on a fresh DB).

**Does NOT catch:** anything Supabase-specific — real `auth.users` trigger
behavior, RLS interaction with `service_role`, FK cascades that only fire
because of Supabase's default schema, extension availability on the
actual Supabase Postgres image. That gap is what `gdpr-supabase.yml`
closes.

Runs on every PR + push that touches the relevant paths. Cheap (no
external service), so always-on.

> **Note on `GDPR_REAL_DB_URL`:** at the test layer both real-DB suites
> gate on this env var. CI never reads it directly from a secret of the
> same name — the local-Postgres job exports it from the ephemeral
> cluster it builds in-runner (`scripts/test-gdpr-real-db.sh`), and the
> real-Supabase job exports it from `SUPABASE_STAGING_DB_URL`
> (`scripts/test-gdpr-supabase.sh`). The deliberate split between two
> secret names — `SUPABASE_DB_URL` for application reads,
> `SUPABASE_STAGING_DB_URL` for the destructive CI fixture — keeps the
> production database from ever being a one-typo-away target for a
> `delete from auth.users`.

## `gdpr-supabase.yml` — real-Supabase real-DB regression

Runs the same two vitest files as `gdpr-real-db.yml`
(`gdpr-roundtrip-realdb.test.ts` + `cap-race-realdb.test.ts`), but
pointed at a real Supabase project via the `SUPABASE_STAGING_DB_URL`
secret. Re-applies every migration first (idempotent per `replit.md`
user preferences), verifies the `delete_user_data()` return signature
against `pg_proc`, then runs both suites in a single vitest invocation
to amortize connection setup.

### Which secret / which project

This job uses **`SUPABASE_STAGING_DB_URL`**, NOT the existing
`SUPABASE_DB_URL` secret. They are deliberately separate names because
the test fixture is destructive: `beforeEach` issues `delete from
auth.users` and `delete from public.<every per-user table>` against the
target database. Pointing it at production would wipe every user.

The expected wiring is a dedicated Supabase project that's a structural
clone of production (same migrations, no real user data). Provision steps:

1. Create a new Supabase project named `nc-gdpr-staging` (or similar).
2. Copy its pooled connection string into the GitHub Actions secret
   `SUPABASE_STAGING_DB_URL` at the repo level.
3. Do **not** populate it with production data. The job assumes it owns
   the database and will repeatedly truncate it.

If the secret is unset, the job logs a `::warning::` and exits cleanly
so a fresh fork or a contributor without secrets access still gets a
green check. The local `gdpr-real-db.yml` job remains the
always-required guard.

### Gating

This job is destructive and burns Supabase project quota, so it is not
on every PR. It runs when:

| Trigger                                          | Behavior                                |
| ------------------------------------------------ | --------------------------------------- |
| push to `main`                                   | Always runs (post-merge regression).    |
| `workflow_dispatch`                              | Always runs (manual rerun / debug).     |
| pull_request labeled `run-gdpr-supabase`         | Runs (opt-in pre-merge verification).   |
| pull_request without that label                  | Skipped.                                |

A `concurrency` group (`gdpr-supabase-staging`) serializes runs so two
jobs can never race each other on the shared staging DB.

### Safety belts in the script

`scripts/test-gdpr-supabase.sh` refuses to run unless:

- `SUPABASE_STAGING_DB_URL` is set,
- the operator passes `I_UNDERSTAND_THIS_WIPES_DATA=yes` (the workflow
  sets this; running the script locally requires you to opt in
  consciously),
- the URL does not contain the substrings `prod` / `production` / `PROD`
  (a heuristic last-line-of-defence in case the wrong secret value is
  pasted in).
